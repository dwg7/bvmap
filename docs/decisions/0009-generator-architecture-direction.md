# 0009: ジェネレーター・アーキテクチャの方針(ケース・カンファレンスの結論)

このADRは、色・フォント・スプライトの生成方式について行ったケース・カンファレンス形式の検討([STARLIGHT_EXPLORATION.md](../STARLIGHT_EXPLORATION.md)の判断事項1)の結論を記録する。

## 結論

**ジェネレータを持つか否かを今すぐ一括で決めない。** 代わりに、検証ゲート付きの段階的な進化を採用する。

### Stage 0(現在地): 純粋な変換スクリプト

新しい抽象化・スキーマを一切持たず、既存JSONを直接変換するスクリプト(暖色ティント変換のような)。新しいスキーマが無いので「関数設計を間違える」リスクがそもそも無い。今回のセッションで行った調査・変換はすべてこの段階。

### Stage 1(次の一歩): 再現優先のジェネレータ

構造化されたソース(下記の理由によりYAML)から、**既存の`bvmap-dark.json`/`bvmap-starlight.json`を意味的に寸分違わず再現できることだけ**を最初の目標にする。新しい表現力を持たせず、「別の形で書き写せる」ことだけを証明する。

### Stage 2以降: 一度に一つの意味的な軸だけを追加

追加する軸は必ず、**既に確認済みの踏み跡に基づくものに限り**、仮説上の将来ニーズでは追加しない。追加のたびに生成結果を既存JSONと突き合わせて検証する。

## 核となる抽象化: 「`vt_code`対応表→`match`式」コンパイラ

色(Anno濃淡ランプ)・フォント(水域/海岸名の明朝体分岐)・アイコン選択(`icon-image`/`icon-size`)は、**GSI自身が既に同じイディオムで実装していた**: 「`vt_code`の集合→値、という対応表を`match`式として複数レイヤーへ適用する」。これは発明ではなく、元データに既にあった統一を見つけたもの。

ジェネレータの核は、色・フォント・アイコンそれぞれに別々の仕組みを作るのではなく、**この一つの共通コンパイラ**(`{vt_codeの集合 → 値}`の対応表を受け取り`match`式を吐く)であるべき。

一方、**スプライトの「独自SDFアイコンを作る」作業(SVG→`spreet`でアトラス化)はこれとは全く別種の仕事**(画像アセットのビルドパイプライン)であり、同じジェネレータに混ぜ込まない。

## 破綻を防ぐ構造的な工夫

- ジェネレータを入れても、**生成されたJSON自体は必ずコミットし続ける**。ジェネレータが壊れても、JSON側を直接手で直せる逃げ道を常に残す。`hfu/stars`側のデプロイもジェネレータの実行に依存させない
- 関数は「色を決める・フォントを決める・アイコンを決める」で分離し、ひとつの巨大な「レイヤーを組み立てる関数」にしない

## 実データから確認した、ジェネレータが対応すべき現実的な制約

1. **「ほぼ同一+一部だけの例外」を前提にする**([0008](0008-cartographic-layer-ordering.md)参照)。道路ティア0の`line-color`例外、注記ソート順100未満のズーム14例外——独立した2箇所で同じ「共有テーブル+疎な例外」というGSIのワークフローの癖が確認された。完全な純粋テンプレートを前提にすると破綻する
2. **`vt_code`(意味語彙)と`symbol-sort-key`(実装上の連番)を明確に分ける**。`vt_code`はGSIの地物コード表に紐づく本物の意味語彙で、欠番も含めて意味を持つ。`symbol-sort-key`は195/199の値が8〜204にほぼ隙間なく詰まった、導出物的な連番——生の数値ではなく「優先順位付きのカテゴリのリスト」として持ち、実際の連番はジェネレータ側で機械的に導出する
   - **確認済み: `symbol-sort-key`は逃げ場のないジェネレータの責任範囲**。(a) タイル側のフィールドスキーマ(`Anno`: `vt_arrng`/`vt_arrngagl`/`vt_code`/`vt_dsppos`/`vt_flag17`/`vt_text`)に優先順位を表す属性は存在しない——タイルから読めない。(b) `text-size`のグループ分けとの相関を実測したところ弱く(例: `text-size=24`のグループだけでも sort-key は14〜192まで分散)、他のスタイル属性から機械的に導出することもできない。つまり`vt_code`ごとの優先順位は、GSIが完全に独立した編集判断として決めた、他から借りてこられないデータであり、ジェネレータの入力として明示的に持つ以外に選択肢が無い
3. **道路・鉄道・建物の複合ティア構造**は`vt_lvorder`(0/1/2/3/≥4)で駆動され、各ティア内部に固定の14レイヤーの並び(地上道路→地上鉄道→地上橋梁道路→建物→高架鉄道)を持つ。テンプレート化の第一候補

## 入力形式: YAML

理由:
- `vt_code`のリストにはGSIの地物コード表由来の意味(例: 「湖・沼・池・浦等」)があり、JSONにはコメント構文が無い。YAMLならコメントとして意味メタデータを値のそばに残せる
- `hfu/stars`自身が既に`config/martin.yaml`でYAMLを使っている(生態系内の一貫性)

コメントは**人間向けの説明文ではなく、将来のAIセッションがGSIの資料を再度漁らずに済むための構造化された意味メタデータ**として書く([フィードバック記録](../../.claude/../CLAUDE.md)参照、または`~/.claude/projects/-Users-hfu-bvmap/memory/feedback_ai_consumable_documentation.md`)。

## `@unvt/charites`との違い(重複ではないことの確認)

`unvt/charites`(MIT、現役)を実際に調査した結果、そのYAMLは**Mapbox/MapLibre style-specの語彙・粒度をそのまま保った表記糖衣**(`id`/`type`/`paint`等がキー)で、マクロもファイル分割と単純な文字列置換の2つのみだった。1つのYAML定義=1つのstyle-specレイヤーという1:1対応を崩していない。

今回考えているものは、`vt_code`というGSIデータ自体の意味論を第一級の語彙として持ち、そこから色・フォント・アイコンという複数のstyle-spec出力を同時に導出する、一段上の抽象化であり、Charitesとは異なる層の問題を扱う。
