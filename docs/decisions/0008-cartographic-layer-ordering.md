# 0008: 地図学的レイヤー順序体系(bvmap-darkの実装から帰納)

## 目的と方法論

`bvmap-dark.json`の123レイヤーの重ね順は、これまで暗黙の配列順序でしか表現されていなかった。このADRは、実装(配列順序・filter式・実際のタイルデータ)を探索的に調査し、**既存の実装を説明可能な体系**として記録する。

重要な方法論上の注意: style.jsonのレイヤー順序には、**意味のある重なり**(2つの地物が実際に空間的に重なり得て、描画順が視覚的結果を左右する)と、**見かけ上の重なり**(2つのレイヤーが実際には重ならないため、配列上の前後関係が偶然にすぎない)が混在しうる。本ノートの順序体系は、前者だけを拾うよう、可能な限り実データで検証してから確定させた。

## 検証: 行政区画面と陸水面の関係(仮説は誤りだった)

当初「`AdmArea`(行政区画)と`WA`(水域)は同時に出現しないようタイルが設計されている(見かけ上の順序)」という仮説があったが、実タイル(z14, 小樽沖、`https://stars.optgeo.org/bvmap/14/14608/6008`)を取得し`mapbox_vector_tile`+`shapely`で検証したところ、**否定された**:

- `AdmArea`は穴のない単一ポリゴンでタイル全域をほぼ覆う
- `WA`(水域)は`AdmArea`の内側に100%含まれる(交差面積/WA面積 = 1.0)
- `AdmArea`の`fill-color`は不透明な白(`rgba(255,255,255,1)`)

つまり`AdmArea`は水域を含む行政区画全体を塗る下地であり、`WA`はその上から水域を塗り直す。**もし順序を逆にすれば水域は完全に隠れる**——これは意味のある重なりであり、見かけ上のものではなかった。`AdmArea`は独立した「行政区画面」というより、**「背景面のすぐ上にある、行政区画全体を覆う下地」**として、事実上`background`の延長として機能している。

### `background`・`AdmArea`・`WA`の「踊り」

`background-color`は`["step", ["zoom"], "rgba(255,255,255,1)", 4, "rgba(209,209,209,1)", 8, "rgba(255,255,255,1)"]`——**白→ズーム4でグレー(209)→ズーム8で再び白**、という不思議な段差になっている。`AdmArea`/`WA`のソースデータの`minzoom`は共に4(TileJSON確認済み)。`AdmArea`の`fill-color`は常に不透明な白で、ズームによる変化は無い。これらを重ねると、3層が最小限のデータで陸と海を塗り分ける仕組みが見えてくる:

- **ズーム0-3**: `AdmArea`データがまだ存在しない(`minzoom:4`)。背景は白一色。小縮尺では海が視界を支配するため、陸の輪郭を精密に描く必要が無く、コストをかけずに済ませられる
- **ズーム4-7**: 背景がグレー(209)に反転。`AdmArea`の白いポリゴンが、行政管轄(≒陸+管轄水域)がある場所だけ上から白く塗る。**行政管轄が無い場所(外洋)はグレーのまま透けて見える**——これが「陸か海か」の区別そのものになる。専用の「海ポリゴン」データを持たずに、`AdmArea`の有無というコントラストだけで陸海を塗り分けている
- **ズーム8以上**: 背景が白に戻り、`AdmArea`の白と同化して視覚的には消える(実際には描画され続けているが、白の上に白を塗るだけで効果が無い)。この時点で`WA`が実際の水域データを詳細に描き始めるため、「陸海の区別」という役目は`WA`に完全に引き継がれる。大縮尺(市街地レベル)では誰も外洋を注視しないため、`AdmArea`の白と背景の白が同化して見分けが付かなくなっても実害が無い

つまり「背景色がズームで反転する」のは装飾ではなく、**`AdmArea`データが使える範囲(ズーム4-7)でだけ、背景とのコントラストを使って安価に陸海を塗り分け、それ以外の範囲では自然にフェードアウトする**という、3層一体の設計だった。

### 訂正: `WA`内部の「海」と「内水面」の扱い(初回の推測は誤りだった)

`bvmap-水域`の`fill-color`は`rgba(209,209,209,1)`——**背景のズーム4-7と全く同じグレー**。`fill-opacity`は次の式で、特定の`vt_code`をズーム11未満で不透明度0(非表示)にしている:

```json
["interpolate", ["linear"], ["zoom"],
  10, ["case", ["in", ["get","vt_code"], ["literal",[5201,5202,5203,5211,5212,5290]]], 0, 1],
  11, 1]
```

**初回の推測**(このADRの草稿時点)では、非表示にされる`vt_code`群を「大きな海ポリゴン」と予想し、「`AdmArea`との対比で既に陸海が伝わっているズーム帯では、重い海ポリゴンの描画を省略するコスト最適化」という理論を立てた。

GSIの公式地物コード表(`https://maps.gsi.go.jp/help/pdf/vector/optbv_featurecodes.pdf`)を実際に確認したところ、**この推測は誤りだった**。`vt_code` 5201/5202/5203/5211/5212は「51=海」ではなく**「52=河川・湖池」**(河川・湖の通常部/岩や堤防に接する部分/河口部/湖池界線)、つまり**内水面**を指すコードだった。海(51xx)は除外リストに含まれず、常に不透明度1のまま描画され続けている。

正しい説明: **内水面(河川・湖)は数が多く個々の面積が小さいため、ズーム11未満(広域表示)ではノイズになるだけで意味が薄く、非表示にして描画コストと視覚的な煩雑さを避けている**。一方、海は数少ない・面積の大きいポリゴンであり、どのズームで見ても常に意味を持つため、最初から常時描画で構わない。「省くメリットが大きいのはどちらか」という問いへの答えは、海と内水面の**数と大きさの非対称性**にあった。

なお、`内水面は行政区画に含まれる必要がある`(藤村さんの指摘)一方、`海洋は法令上は行政区画に含まれないが、実務上のデータでは行政区画に含まれている場合がある`という留保も踏まえると、[前節で検証した](#検証-行政区画面と陸水面の関係仮説は誤りだった)「`WA`が`AdmArea`に100%内包される」という実タイルでの観測結果は、そのタイルにたまたま内水面(または実務上行政区画に含まれる海域)しか含まれていなかった可能性がある。**「海が`AdmArea`に含まれるかどうか」は、タイルによって異なりうる**——これは今後、複数の沿岸タイルで再検証すべき論点として残す。

## 確定した順序体系(下から上)

1. **背景面** (`background`)
2. **行政区画面** (`AdmArea`) — 上記の通り、事実上の背景延長。水域・被覆面の下地
3. **陸水面** (`WA`ほか水域fill)
4. **被覆面** (`TpgphArea`等、地形表記面)
5. **陸水面・被覆面付随の線群** (`Cstline`海岸線、`RvrCL`河川中心線、`WL`水涯線、`WRltLine`水部表記線等) — このデータセットでは独立した段になっておらず、3・4と混在して出現する
6. **行政区画線** (`AdmBdry`) — 独立層。道路群の直前に位置する
7. **等高線・等深線** (`Cntr`、`Isbt`)
8. **道路・鉄道・建物の複合ティア構造**(詳細は次節)
9. **構造物・送電線等** (`StrctArea`/`StrctLine`/`PwrTrnsmL`)
10. **特定地区界** (`SpcfArea`) — 面として閉じておらず実質的に地図記号に近い。存在感が薄く、この位置(構造物付近)にあっても違和感はない
11. **記号点** (`WRltLine`のpoint、`Cntr`/`Isbt`の数値ラベル)
12. **注記** (`Anno`由来の全シンボルレイヤー)

`bvmap`シリーズとしての**空きスロット**(GSI原版には存在しない): 主題面・主題線・主題点。sas0のようなダッシュボード用途で、後から意味のあるレイヤーを挿入するための予約位置。位置の候補は8(道路等)と9の間、9と10の間、12の後、など。**これらの空きスロットを実際にどう「印」として残すか(何もしないマーカーレイヤーを置き、MapLibreの`addLayer(layer, beforeId)`で挿入先として使う等)は、まだ実装方法が確立されていない**——将来のADRで扱う。

## 道路・鉄道・建物の複合ティア構造(詳細)

`vt_lvorder`(0/1/2/3/≥4)という明示的な属性が、立体交差の上下関係を表す。**73レイヤー**(低ズーム概観用3レイヤー+14レイヤー×5ティア)がこの一塊を構成する。

各ティアNの内部構造(下から上):

```
道路ククリ(N)、道路色(N)                    — 地上の道路(ケーシング+塗り)
鉄道駅ククリ(N)、鉄道(N)、鉄道旗竿(N)         — 地上の鉄道(旗竿=JR専用の目印記法)
道路ククリ橋(N)、道路色橋(N)                 — 地上区間の橋梁部分の道路
建築物(N)、建築物の外周線(N)                 — 建物(地上インフラと高架インフラの間)
鉄道橋ククリ黒(N)、鉄道橋ククリ白(N)、
鉄道橋駅ククリ(N)、鉄道橋(N)、鉄道旗竿橋(N)    — 高架鉄道(建物の上、現実の立体構造を反映)
```

建物が「地上インフラ」と「高架インフラ」の間に挟まる配置は偶然ではなく、現実の立体的な位置関係(地上の道路・鉄道→建物→建物を跨ぐ高架)を反映した設計と考えられる。

**完全な同一テンプレートではない**: `paint`はティア間でほぼ同一だが、**ティア0の道路`line-color`だけ「`vt_rnkwidth`が不明な道路は透明にする」という追加の`case`分岐**があり、ティア1以降には無い。ジェネレータはこの「ほぼ同一+一部ティアだけの例外」という現実的な形を許容できる設計にする必要がある(完全な純粋テンプレートを前提にすると破綻する)。
