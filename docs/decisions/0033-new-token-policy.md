# 0033: 新規パレットトークンの方針(0032移行作業の前提)

[0032](0032-literal-layers-generator-migration-plan.md)の実装に入る前に、Fableレビューが浮かび上がらせた2つの論点をケース・カンファレンスで決定した。

## 決定1: 新規トークンにも0030の変換を最初から適用する

移行で新設する全てのパレットトークン(地形表記面の217/239、水部表記線lineの99、行政区画界線の35/27、特定地区界の150、等)は、[0030](0030-starlight-first-color-pass.md)の`cool_transform()`(明るく・銀灰色寄り)を**最初から適用した値**で追加する。生の`bvmap-dark`値のまま追加し後で一括変換する、という二段階は取らない。

**理由**: [0003](0003-bvmap-starlight-naming.md)の「一貫性を持って仕上げる」という方針そのもの。既存29トークンだけ変換され、新規トークンが素の`bvmap-dark`値のままという状態は、Fableレビューが指摘した通り「見えない改善のはずが、気づかれないまま元の配色が混在する」という結果を生む。

## 決定2: 偶然同値のトークンは、デフォルトでは流用しない

移行対象の生の値が既存トークンと数値上一致していても(地形表記面の233↔建物塗り`gray_233`、水部構造物面の200↔道路幅員ランプ`gray_200`等)、**その一致が実データで検証済みでない限り、独立したトークンとして追加する**。

**理由**: [0020](0020-yaml-wiring-stage1.md)の`narrow_exception_color`の教訓(「値が偶然一致しているだけで意味的に同じとは限らない」)をそのまま適用する。流用してしまうと、将来「建物の塗りだけ少し明るくしたい」という編集が、無関係な地形表記面の色まで意図せず動かしてしまう。

**例外(流用してよい場合)**: [0022](0022-zl4-10-and-post-tier-layers-footprint.md)で確認した`gray_88`/`gray_161`のように、**同じvt_codeが複数のレイヤー機構(共有ランプ側と独立レイヤー側)で使われていることが実データで検証済み**なケースは、意図的な一致と判断してよい。判定基準は「値が同じ」ではなく「同じvt_code、あるいは同じ意味領域だと実データ・ADRで裏付けられているか」。

## 命名規則

- 既存の`gray_<変換前の生の値>`という命名は維持する(トレーサビリティのため)
- 新規トークンの生の値が既存トークン名と衝突する場合(例: 地形表記面の233は`gray_233`と衝突)、意味領域を示す接尾辞で区別する(例: `gray_233_terrain`)。衝突しない場合はそのまま`gray_<値>`でよい
- `gray_100`/`gray_255`は[0010](0010-color-semantic-categories.md) §4で既に「62レイヤー横断の汎用色、単独の意味を持たない」と明記されている——この2つは決定2の対象外とし、引き続き自由に流用してよい。一方`gray_88`は Anno group_b・等深線数値部という具体的な意味を持つため、汎用トークン扱いはしない

## 陸水面・被覆面付随の線群(0008)での88/100の扱い

`水涯線`・`水部構造物線`・`海岸線`・`河川中心線`・`地形表記線`(いずれも[0032](0032-literal-layers-generator-migration-plan.md)のGroup A/B/Eに属する)は、[0008](0008-cartographic-layer-ordering.md)で「陸水面・被覆面付随の線群」として1つのまとまりだと確認済みのクラスタ。このクラスタ内で88/100が繰り返し使われているのは、決定2の例外(意味領域が実データ・ADRで裏付けられている)に該当すると判断し、クラスタ専用の共有トークン(`gray_88`/`gray_100`とは独立)を1組新設し、クラスタ内で共有してよいこととする。実際のトークン名・値は実装時に確定する。
