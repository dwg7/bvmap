# 0015: 「統一」と「意味分割」の場(統合ケースの結論)

このADRは、ケース・カンファレンス([STARLIGHT_EXPLORATION.md](../STARLIGHT_EXPLORATION.md))の最後に残った統合的な問い——「デザイン統一」と「セマンティック分割」という2つの力が働く"場"をどう認識し、どう実装するか——の結論を記録する。方針通り、個別ケース(色・フォント・スプライト)を先に決めてから、最後に帰納的にこの問いへ戻った。

## 当初の仮説

粗く統一しつつ、動的に意味分離できる余地を残す。具体的にはMapLibreのglobal-state式(v5.6+、v6.1でsky/light/projectionにも波及)で、既定は統一状態、対応クライアント側でフラグを立てれば意味的な分離が蘇る、という実装を想定していた。

## 6ケースを振り返って見えたパターン

[0009](0009-generator-architecture-direction.md)〜[0014](0014-sprite-decisions.md)の6ケース全てが、共通の形を取っていた:

| ケース | 統一(選んだ側) | 意味分割(見送った側、ただし記録は残す) |
|---|---|---|
| 1. 生成方式 | 段階的進化、核は1つのコンパイラ | 複数の専用ジェネレータ |
| 2. 色 | 意味のあるランプだけ昇格、他はdefault | 全色を個別に意味付け |
| 3. フォント実装 | 実フォント名直書き | `font-faces`自前ホスティング |
| 4. 斜体 | 諦める(他の軸へ) | 斜体という軸の維持 |
| 5. 紙地図復活範囲 | GSI公式デジタル版のまま | 自然地形全般への拡張 |
| 6. スプライト | 絵文字・独自SDF見送り | パレットを崩す拡張 |

**6ケース全てが、統一(単純)側を選びつつ、意味分割に必要な材料(`vt_code`一覧、技術的前提条件)をADRとして記録する**、という同じ形を取っていた。

## 結論: 仮説は部分的に正しく、精緻化が必要だった

「粗く統一しつつ、動的に意味分離できる余地を残す」という構造そのものは、6ケース全てで確認された。ただし「動的」の中身が当初の想定と異なっていた:

- **当初の想定**: MapLibreのglobal-state式による、実行時(ランタイム)のフラグ切り替え
- **実際に機能していたもの**: `docs/decisions/`のADRという**文書記録を介した、セッションをまたいだ切り替え**。意味分割に必要な材料(拡張候補の`vt_code`一覧、技術的な前提条件の調査結果)をADRに残すことで、将来のセッション(人間またはAI)が、コードを触ることなく意味分割を再開できる状態を作っていた

global-state式は技術的に利用可能なオプションとして確認済み([STARLIGHT_EXPLORATION.md](../STARLIGHT_EXPLORATION.md)の初期調査)だが、6ケースのどこにも、実行時に統一/分割を切り替える具体的な必要性は無かった。**「動的」は「実行時」ではなく「セッション間」の話だった**、というのが今回の帰納的な結論。

## 今後の含意

- 新しい判断が必要になった時も、同じ形(まず統一側を選び、分割に必要な材料をADRに残す)を踏襲してよい
- global-state式による実行時切り替えは、具体的な必要性(例: 同一デプロイで「シンプルモード」と「詳細モード」を利用者が切り替えたい、という要求)が生じた時に初めて検討する。今の時点で先回りして実装しない
- [0008](0008-cartographic-layer-ordering.md)で触れた「主題面・主題線・主題点」の空きスロット(マーカーレイヤーによる挿入点)は、この統合ケースとは別種の「動的」(実行時にレイヤーを追加する)であり、混同しないこと
