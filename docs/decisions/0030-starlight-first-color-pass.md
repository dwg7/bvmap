# 0030: Starlight配色磨き上げ、最初の一手

[0029](0029-assemble-writes-starlight-json.md)で書き出しパスを整えた後、`starlight-input.yaml`のpaletteに実際に最初の変換をかけた。「いったん実装してみて、後でさらにエレガントな方法があれば考える」という前提で進めた第一稿。

## 適用した変換

全パレットトークン(`transparent`・`black`・`gray_255`を除く、29トークン)に対して、次の2段階変換を機械的に適用した:

```python
def cool_transform(r, g, b, cool=2.2):
    v = (r + g + b) / 3
    brighten = 0.03 if v < 100 else 0.09  # 暗い値(注記の重要度ランプ等)は控えめに、
                                            # 明るい値(道路・建物等)はより強く明るくする
    r2 = r + (255 - r) * brighten
    g2 = g + (255 - g) * brighten
    b2 = b + (255 - b) * brighten
    b2 += cool          # 青方向へわずかにシフト(銀灰色寄り)
    r2 -= cool * 0.6    # 赤方向を少し引く
    return (round(r2), round(g2), round(b2))
```

- **`black`・`transparent`・`gray_255`(白)は変換対象外**: 黒は注記の視認性(コントラスト)、白は背景の清潔さを保つため、意図的に据え置いた
- **2段階のbrighten率**: 明度100未満(注記の重要度ランプ等、可読性が特に重要な値)は3%、100以上(道路・建物等)は9%——暗い文字色を大きく明るくするとコントラストが落ちて可読性を損なうため、非対称にした
- **cool=2.2**: R成分を約1.3引き、B成分を2.2足す、微弱な寒色シフト。ADR[0003](0003-bvmap-starlight-naming.md)の「銀灰色寄り」を、派手な色相変化ではなく**ほぼ気づかない程度の質感の変化**として表現することを狙った

## 適用例(検証済み、数値ベース)

| トークン | 旧値 | 新値 |
|---|---|---|
| `gray_100`(62レイヤー横断の汎用色) | 100,100,100 | 113,114,116 |
| `anno_29`(注記最重要ランプ) | 29,29,29 | 34,36,38 |
| `gray_233`(普通建物塗り) | 233,233,233 | 234,235,237 |
| `gray_161`(等高線・c7352) | 161,161,161 | 168,169,172 |

Anno重要度ランプ(29〜98の9段階)の相対順序は変換後も保たれることを確認済み(順序が崩れると読みやすさの階調が壊れるため)。

## 検証

`generator/assemble.py`を実行し、`style/bvmap-starlight.json`へ書き出し。42レイヤーが`bvmap-dark.json`と内容差分を持つことを確認(想定通り——構造は変えていないので、id順・レイヤー数は完全一致のまま)。`examples/style-preview.html`(ローカル`python3 -m http.server 8765`)で実際にbvmap-dark/bvmap-starlightを切り替えて目視確認——道路・建物がわずかに明るく、わずかに寒色寄りになっていることを確認した(効果は意図的に控えめ)。

## 今後の余地

- 効果が控えめすぎる/強すぎるという評価があれば、`brighten`/`cool`のパラメータを調整するだけで全体を再生成できる(pale​tteセクションを触るだけで済む設計が効いている)
- 現在は全トークンに同一の機械的な変換式をかけただけで、個々の意味(例: 高速道路と一般道の明度差が縮まりすぎていないか等)を精査してはいない——実際の見た目で気になる箇所があれば、個別トークンの手動調整に切り替える
- `black`(注記のdefault)や道路・鉄道の橋梁アルファ(0.5)等、変換の対象外にした値も含めて、全体のバランスは今後の目視確認で継続的に調整する
