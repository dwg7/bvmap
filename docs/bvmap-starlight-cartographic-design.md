# bvmap-starlight の地図学的設計 — GSI `bvmap-dark` から帰納した図式知識とその継承

2026-09-20時点。対象読者は地図技術者(図式・総描・記号階層の素養はあるが、MapLibre GL JS style-spec や本リポジトリの内部には必ずしも詳しくない方)。本文書は `generator/starlight-input.yaml` の現在の内容と同期しており、引用しているトークン名・`vt_code`・色値はすべて同ファイルおよび `style/bvmap-dark.json` の実データから取っている。個々の発見の一次記録は `docs/decisions/` の ADR 0001〜0035 にあり、本文中で番号で参照する。

## 1. bvmap-starlight とは何か

`bvmap-starlight` は、国土地理院(GSI)の最適化ベクトルタイル(`optimal_bvmap`)向けスタイル `bvmap-dark` を基点にした MapLibre GL JS スタイルである。`bvmap-dark` は `stars.optgeo.org/style/bvmap-dark` として配信されており、その正本は [`hfu/stars`](https://github.com/hfu/stars) の `styles/` ディレクトリにある(Martin tileserver の `config/martin.yaml` が `styles.paths` として直接参照している、[0006](decisions/0006-hfu-stars-is-already-master-repo.md))。本リポジトリ `dwg7/bvmap` はその配信リポジトリではなく、スタイルの**開発・検証ワークスペース**であり、`style/bvmap-dark.json` はある時点のスナップショット(123レイヤー、無加工)、`style/bvmap-starlight.json` はジェネレータの出力である。完成した `bvmap-starlight` は `hfu/stars/styles/` へ PR として反映する(未着手)。

名前の由来は単純で、`bvmap-dark` という識別子に反して実際の見た目は「明るいクリーム地に淡い銀灰色の道路」だった。この実態に近い Apple の製品色名 Starlight を採り、「低彩度・明るめ・銀灰色寄り」へ**一貫性を持って磨き上げる**ことを唯一の目標に据えた([0003](decisions/0003-bvmap-starlight-naming.md)、[0005](decisions/0005-goal-change-master-repo-and-starlight-polish.md))。当初の発端だった縦書き注記の棒音符「ー」問題は、MapLibre 本体のローカルグリフ描画(Canvas 2D の `fillText`)に `font-feature-settings` を渡す経路が無いため userland では解決不能と判明し、目標から外した([0004](decisions/0004-vertical-choonpu-workaround-does-not-work.md))。

重要なのは、この作業が「配色を変える」以前に「**GSI が `bvmap-dark` に何を設計として埋め込んだのかを読み解く**」作業になったことである。123レイヤーの style.json は、地物コード表・レイヤー順序・色の対応表・ズーム帯ごとの切り替えという形で、紙地図以来の図式の判断をかなり忠実に含んでいた。それを言語化してジェネレータの入力(`starlight-input.yaml`)に落とし、色だけを差し替えられる形にした——これが本文書の主題である。

## 2. 方法論 — 実データで仮説を潰しながら帰納する

作業の作法は一貫して「先に枠組みを決めず、実データで検証してから帰納する」だった(HANDOVER.md)。具体的には、(a) `bvmap-dark.json` の式を分解する、(b) `stars.optgeo.org/bvmap/{z}/{x}/{y}` の実タイルを `mapbox_vector_tile` + `shapely` で読む、(c) GSI 公式の地物コード表 PDF(`optbv_featurecodes.pdf`)を実際に取得して突き合わせる、(d) ジェネレータで再現して byte-exact 一致を取る、の4手段を使った。

この過程で、戦略的には筋が通って見えた仮説が何度も覆った。例を挙げると:

- 「行政区画面(`AdmArea`)と水域(`WA`)は同時に出現しない」→ 実タイルで `WA` が `AdmArea` に100%内包されており、順序を逆にすれば水域が消える**意味のある重なり**だった([0008](decisions/0008-cartographic-layer-ordering.md))
- 「水域でズーム11未満に非表示にされる `vt_code` 5201系は海の大ポリゴン」→ 地物コード表で確認すると **52=河川・湖池(内水面)** であり、海(51xx)は常時描画だった(同)
- 「市区町村道等の色は gray(100)」→ それは橋梁 `vt_code`(2704/2714)分岐内だけの値で、一般道の市区町村道等は道路種別ではなく**幅員**で塗り分けられていた([0010](decisions/0010-color-semantic-categories.md)→[0018](decisions/0018-road-color-not-flat-category-compiler.md)で訂正)
- 「軌道(`RailTrCL`)の色分けは表層とトンネルで非対称」→ `vt_code` が「種別2桁+状態1桁」の構造だと分かると、暗くなる種別は両者で完全に一致していた([0022](decisions/0022-zl4-10-and-post-tier-layers-footprint.md)→[0025](decisions/0025-remaining-post-tier-13-layers-footprint.md))

ADR は誤った仮説も消さず訂正として残している。以下の記述は、こうした訂正を経た後の理解である。

## 3. 構造に埋め込まれた地図学

### 3.1 レイヤー順序体系(下から上)

123レイヤーの配列順序を、実データで「意味のある重なり」だけを拾って体系化すると次の12段になる([0008](decisions/0008-cartographic-layer-ordering.md))。

| 段 | 内容 | 主なソースレイヤー |
|---|---|---|
| 1 | 背景面 | `background` |
| 2 | 行政区画面(事実上の背景延長) | `AdmArea` |
| 3 | 陸水面 | `WA` |
| 4 | 被覆面(地形表記面) | `TpgphArea` |
| 5 | 陸水面・被覆面付随の線群(3・4と混在) | `Cstline`、`RvrCL`、`WL`、`WRltLine` |
| 6 | 行政区画線 | `AdmBdry` |
| 7 | 等高線・等深線 | `Cntr`、`Isbt` |
| 8 | 道路・鉄道・建物の複合ティア(73層) | `RdCL`、`RailCL`、`BldA` |
| 9 | 構造物・送電線 | `StrctArea`、`StrctLine`、`PwrTrnsmL` |
| 10 | 特定地区界(面として閉じておらず実質は記号) | `SpcfArea` |
| 11 | 記号点・数値ラベル | 等高線数値部、流水方向 |
| 12 | 注記 | `Anno`(9層) |

紙地図の「面→線→記号→注記」という描画順序がそのまま現れており、5段目が独立した段になっていない(面と線が混在する)のは、このデータセットでは水涯線や海岸線が面の輪郭として面と一体で扱われているためと読める。

### 3.2 陸と海の塗り分け — 3層の「メヌエット」

`bvmap-dark` には専用の海ポリゴンが無い。にもかかわらず小縮尺で陸海が読めるのは、`background`・`AdmArea`・`WA` の3層が縮尺帯ごとに役割を交代しているからである([0008](decisions/0008-cartographic-layer-ordering.md))。

```
background-color = step(zoom, 白, 4, gray(209), 8, 白)
AdmArea fill     = 常に不透明な白(データは minzoom 4)
WA fill          = gray(209)、ただし zoom<11 では 52xx(内水面)を不透明度0
```

- **ズーム0-3**: `AdmArea` データが存在しない。背景は白一色。海が視界を支配し、陸の輪郭を精密に描く必要が無い
- **ズーム4-7**: 背景がグレー(209)に反転し、`AdmArea` の白いポリゴンが行政管轄のある場所だけを白く塗る。**管轄の無い外洋はグレーのまま透ける**——これが陸海の区別そのものになる
- **ズーム8以上**: 背景が白に戻り `AdmArea` と同化して見えなくなる。同時に `WA` が実際の水域データを描き始め、役目を引き継ぐ

つまり背景色の反転は装飾ではなく、「`AdmArea` が使える帯域でだけ、背景とのコントラストで安価に陸海を塗り分ける」データ経済の設計である。また `WA` の内水面(5201/5202/5203/5211/5212/5290)がズーム11未満で消えるのは、数が多く面積の小さい内水面が広域表示ではノイズになる一方、海は数少なく面積が大きいのでどのズームでも意味を持つ、という**数と大きさの非対称性**に基づく総描判断である。

この交代は比喩以上に精密で、メヌエットの「一方が前へ出る間もう一方は退く」という形式的な掛け合いに近い——白(背景単独)→白とグレーのコントラスト(背景とAdmArea)→白とWA(背景が退きWAが主役を継ぐ)という進行は、メヌエットとトリオのABA的な三部構成にも重なる。

この3層は `starlight-input.yaml` では `patches` に「被覆面ダンス」として注釈付きで登録され、色だけが `gray_255` / `gray_209` のトークンで駆動されている。

### 3.3 道路・鉄道・建物の複合ティア — 立体交差を現実の高さ順に描く

道路・鉄道・建物は、`vt_lvorder`(0/1/2/3/≥4)という「立体交差の上下関係」属性で5つのティアに分かれ、各ティアが14ロールの固定の並びを持つ。合計 3(ZL4-10)+14×5 = 73層がひと塊である。ティア0の内部順序は次の通り(`generator/tier_template.py` の `ROLES_TIER0`):

```
道路中心線ククリ / 道路中心線色           — 地上道路(ケーシング+塗り)
鉄道中心線駅ククリ / 鉄道中心線 / 鉄道中心線旗竿 — 地上鉄道
道路中心線ククリ橋 / 道路中心線色橋       — 地上区間の橋梁部分
建築物 / 建築物の外周線                  — 建物
鉄道中心線橋ククリ黒 / 橋ククリ白 / 橋駅ククリ / 鉄道中心線橋 / 旗竿橋 — 高架鉄道
```

建物が「地上インフラ」と「高架鉄道」の間に挟まっているのは偶然ではなく、現実の立体的な位置関係(地上の道路・鉄道 → 建物 → 建物を跨ぐ高架)の反映と考えられる。ただし実装して初めて分かったのは、**この配置はティア0だけ**で、ティア1〜4では建物が最後(高架鉄道の上)に来ることである([0016](decisions/0016-tier-generator-stage1.md))。ティア0は地表面に相当するため建物との前後関係が実際に問題になるが、ティア1以上は既に「何かの上」なので簡略化した、と読める。

紙地図の記法も残っている。`鉄道中心線旗竿`は `vt_rtcode == "JR"` のみを対象に、暗い本線の上へ白の破線 `[5,5]` を重ねる——地形図の JR 線記号(白黒の交互塗り)そのものである。鉄道の `line-width` は `vt_rtcode`(JR/JR以外 600、地下鉄 500、路面・索道 400、特殊鉄道・側線 300)と `vt_sngldbl`(複線以上・駅部分で2倍)で決まり、駅部分は白で塗って駅の範囲を線上に示す。

### 3.4 低ズーム概観(ZL4-10)からティア構造への引き継ぎ

ティア構造の全レイヤーは `minzoom: 11`、一方 `bvmap-道路中心線ZL4-10国道`・`ZL4-10高速`・`bvmap-鉄道中心線ZL4-10` の3層は `maxzoom: 11` である。**ズーム11でちょうど引き継ぐ**([0022](decisions/0022-zl4-10-and-post-tier-layers-footprint.md))。個々の橋が視認できないズームでは立体交差を気にせず1本線で済ませ、視認できるズームで初めて5ティアに展開する。これは陸海の3層ダンスと同じ「縮尺帯ごとに必要十分な仕組みだけ動かす」設計思想である。

ただし ZL4-10 はティアの単純な低解像度版ではない。橋梁判定の `vt_code` 集合が `[2704,2714,2724,2734]` とティア(`[2704,2714]`)より広い、橋梁分岐内の都道府県道が gray(100)(ティアでは 226)、「主要道路」というティアに出てこない `vt_rdctg` 値が国道と同グループにされている、判定のネスト順序が逆、さらに国道層と高速層で `vt_motorway` チェックの有無という構造レベルの差がある([0024](decisions/0024-zl410-dedicated-module.md))——独立に設計された概観図式であり、ジェネレータでも `zl410_kokudo_road_color` / `zl410_kosoku_road_color` として別テーブルに保った。

### 3.5 `vt_code` の内部構造と、横断的な詳細化フラグ

GSI 公式地物コード表で確認した事実として、線状地物の `vt_code` は「**種別2桁+状態1桁**」の構造を持つ([0025](decisions/0025-remaining-post-tier-13-layers-footprint.md))。軌道(`RailTrCL`)なら種別 01=普通鉄道/11=特殊鉄道/21=索道/31=路面の鉄道/41=側線、状態 1=通常部/2=遮蔽/3=橋・高架/4=トンネル/6=運休中で、`2804` は「普通鉄道のトンネル」を意味する。道路の `27xx` も同様で、種別21=徒歩道、31=石段、状態1〜4が通常/雪覆い/橋高架/トンネルである。

この読み方が分かると、`bvmap-軌道の中心線`(通常部・橋高架・運休中の17コード)と `bvmap-軌道の中心線トンネル`(遮蔽・トンネルの補集合)が状態で分割され、暗い色 gray(30)になる種別は両層とも普通鉄道・特殊鉄道・路面の鉄道の3種別で一致していることが自明になる。「遮蔽」(雪覆い)がトンネル層に入るのは、どちらも「上から見えない区間」という描画上の扱いが同じだからと読める。`bvmap-道路中心線破線` が `[2724,2734]`(徒歩道と石段のトンネル状態)だけを対象にするのも、種別ではなく「トンネル状態」という横断的条件で発火する装飾層だと分かる。

もう一つの横断的機構が `vt_flag17` で、ズーム17を境に filter を `step` で切り替える(`vt_flag17 in [0,1]` → 17未満、`[1,2]` → 17以上)。これは `vt_lvorder`(立体交差)とは独立した「表示詳細度の段階」で、地形表記面・水部構造物線・鉄道トンネル・注記(`シンボル付き重なり`)と、地物の種類を跨いで使われている([0027](decisions/0027-anno-remaining-4-layers-footprint.md))。ズーム17は「1/2,500 地形図相当の詳細に切り替わる」閾値として GSI データ側に用意された仕組みと見てよい。

## 4. 色に埋め込まれた地図学

### 4.1 全てがニュートラルグレー

`bvmap-dark` の色指定は668箇所・43種で、**すべて R=G=B の無彩色**である(`docs/STARLIGHT_EXPLORATION.md`)。色相を持たない図式であり、地物の区別は明度だけで行われている。このため、Starlight の磨き上げは「色相を足す」のではなく「明度の階調を保ったまま、質感をわずかに寄せる」作業として設計できた(第6節)。

### 4.2 道路 — 種別、優先上書き、幅員フォールバックの三重構造

道路の `line-color` はフラットな対応表ではなく、複数属性にまたがる優先順位付きの分岐である([0018](decisions/0018-road-color-not-flat-category-compiler.md))。`starlight-input.yaml` の `priority_chains.road_color` がその値を宣言し、判定順序は `generator/road_color.py` が持つ:

```yaml
priority_chains:
  road_color:
    engine: priority_case_chain
    bridge_vt_codes: [2704, 2714]
    bridge_table:            # 橋梁関連 vt_code のみ、alpha 0.5 で描く
      国道: gray_160
      都道府県道: gray_226
      市区町村道等: gray_100
      高速自動車国道等: gray_157
      その他: gray_100
      不明: gray_100
    general_table:           # 一般道で vt_rdctg 単独で色が決まる3カテゴリのみ
      国道: gray_160
      都道府県道: gray_226
      高速自動車国道等: gray_157
    motorway_color: gray_157 # vt_motorway==1 は種別を問わず優先
    width_ramp:              # 上記に該当しない道路は幅員で塗り分ける
      "2721,2722,2723": gray_173
      "2731,2732,2733": gray_200
    width_ramp_default: gray_255
    narrow_exception_color: gray_173  # zoom<14 限定、vt_rnkwidth=="3m-5.5m未満"
```

図式として読むと、(1) 高速道路相当は種別によらず最優先で一段暗く、(2) 国道・都道府県道・高速自動車国道等は種別で塗り分け、(3) それ以外(市区町村道等を含む大多数)は**種別ではなく幅員**で塗り分ける、という三層の判断である。市区町村道等は種別内の幅員差が大きいため、種別より幅員の方が地図として意味がある——という GSI の判断が読み取れる。橋梁関連 `vt_code` だけ alpha 0.5 で半透明にするのは、橋の下の地物を透かす表現である。

ケーシング(`ククリ`)側にも別の意味がある: `vt_motorway==1` は黒縁、`[2711,2712,2713]` は gray(173) 縁、他は gray(100) 縁で、ティア0のみ `vt_rnkwidth=="不明"` を透明にする例外を持つ。

### 4.3 建物と構造物 — 3段階の塗り、一律の輪郭

建物は `vt_code` によるフラットな対応表で、ジェネレータの核である `compile_match_expression()` がそのまま再現する([0017](decisions/0017-category-table-generator-stage1.md)):

```yaml
categories:
  building_fill:
    engine: flat_match
    groups:
      c3101: {codes: [3101], value: gray_233}   # 普通建物
      c3102: {codes: [3102], value: gray_203}   # 堅ろう建物
      c3103: {codes: [3103], value: gray_152}   # 高層建物
      c3111: {codes: [3111], value: gray_203}   # 普通無壁舎
      c3112: {codes: [3112], value: gray_203}   # 堅ろう無壁舎
    default: transparent
```

普通→堅ろう→高層の順に暗くなる3段階は、地形図の建物記号(普通建物・堅ろう建物・高層建物の塗り分け)を明度で置き換えたものである。輪郭は種別によらず一律 `gray_164`・幅1で、対応表に無い種別は塗りも輪郭も透明になる。この塗り/輪郭は全5ティアで完全に同一であり、ティアの概念とは独立に存在する([0019](decisions/0019-stage1-final-assembly.md))。

構造物(`StrctArea`/`StrctLine`)も同じ形で、`4301→gray_152`、`4302→gray_233`、線は `4201→black`、`4202→gray_100`。外周線 `gray_164` は建物の外周線と同じ値だが、建物と違い `vt_code` に依らず常に描かれるため、意図的に共有トークン化していない。

### 4.4 注記 — 重要度の濃淡ランプと、ズーム14の疎な例外

注記(`Anno`)9層のうち5層(縦・横×ソート順100以上/未満、角度付き線)は、`vt_code` ごとの `text-color` を定めた同一の `match` 式を共有する。これは地名の**重要度を文字の濃さで表す**ランプであり、暗いほど重要である:

```yaml
  anno_text_color:
    engine: flat_match
    groups:
      c521:  {codes: [521], value: anno_29}                     # 最重要
      c312:  {codes: [312], value: anno_42}                     # 山・岳・峰
      group_e: {codes: [511, 522, ..., 3244], value: anno_50}   # 集落・施設等の大群
      group_d: {codes: [333, 346], value: anno_59}
      water_coastal: {codes: [321, 322, 341, 344, 345, 820, 840, 841], value: anno_68}
      group_a: {codes: [411, ..., 2941, 2942, 2943, 2944, 2945], value: anno_70}
      c220:  {codes: [220], value: anno_80}
      group_b: {codes: [7372, 7711], value: gray_88}
      c348:  {codes: [348], value: anno_98}
      c7352: {codes: [7352], value: gray_161}                   # 等高線数値
      group_c: {codes: [2901, 2903, 2904], value: gray_255}     # 道路番号(白抜き)
    default: black
```

道路番号(2901/2903/2904)が白なのは、道路番号記号の地色の上に白文字で乗せる紙地図の記法を継いでいる。書体は `text-font` で分岐し、水域・海岸名(`[321,322,341,342,344,345,347,820,840,841,842]`)だけ `NotoSerifJP-SemiBold`(明朝)、他は `NotoSansJP-Regular` である。これは 2万5千分1地形図図式 第73条の「自然地形は傾斜体、行政・人工物名は直立体」という慣習を、GSI がデジタル化の際に「水域名だけ明朝体」へ単純化したものと解釈している(`docs/STARLIGHT_EXPLORATION.md`、[0013](decisions/0013-paper-map-revival-scope.md))。和文フォントには本物の斜体が存在しないため、Starlight でも傾斜体の軸は諦め、必要なら書体・ウェイト・色で表現する方針にした([0012](decisions/0012-italic-axis-abandoned.md))。

注目すべきは、色の「水域・海岸」カテゴリ(8コード)とフォントの「水域・海岸」カテゴリ(11コード)のメンバーシップが一致しないことである。342/347/842(海岸・浜・半島系)はフォントでは明朝だが色ではdefault(黒)に落ちる([0017](decisions/0017-category-table-generator-stage1.md))。同じ概念名で呼びたくなるものが、プロパティごとに異なる集合を持つ——ジェネレータもこれに合わせ、カテゴリをプロパティごとに独立して定義している。

`シンボル付き`2層は、この共有ランプを `let` で包み、その上に「ズーム14を境に特定 `vt_code` を透明にする」オーバーレイを被せていた([0027](decisions/0027-anno-remaining-4-layers-footprint.md)):

```yaml
  anno_symbol_text_color_100_under:
    engine: nested_match
    base_category: anno_text_color
    hide_below_zoom14: [631, 632, 633, 6368, 6376]
    hide_at_zoom14: [3212, 3213, 3214]
```

つまり、ある施設名は広域では非表示で詳細で現れ、別の施設名は逆に詳細では消える。ランプ(重要度)とズーム帯(総描)を分離して重ねた設計である。同じ2層の `text-size` にも、優先度の高い`100未満`側だけ「ズーム14で 2941/2942 を1.3倍」という1行の例外がある([0008](decisions/0008-cartographic-layer-ordering.md))。

なお `symbol-sort-key` の195値は8〜204にほぼ隙間なく詰まっており、意味語彙ではなく何らかの一覧順を採番した導出物と見られる。意味を持つのは `vt_code` の側であり、ジェネレータでも sort-key は「優先順位付きリスト」から機械的に導出する対象と位置づけた。

### 4.5 等高線 — 計曲線・主曲線と、数値ラベルとの同色

`bvmap-等高線` は gray(161)で、ズーム10〜14では `vt_alti % 50 == 0` の線だけ描き、ズーム13以降はその線を幅1.4(他は0.7)にする——**計曲線と主曲線**の区別である。等深線は gray(88)。数値ラベル(`等高線数値部`/`等深線数値部`)の `text-color` はそれぞれ親の線と同じ 161/88 で、しかも同じ `vt_code`(7352/7372)が注記の共有ランプにも単独カテゴリとして同じ値で現れる([0022](decisions/0022-zl4-10-and-post-tier-layers-footprint.md)、[0023](decisions/0023-structure-and-contour-layers-implemented.md))。線と数値を同色に保つのは図式上の基本であり、パレットでは `gray_161`/`gray_88` を両者で共有して連動させている。

### 4.6 パレット — 意味ごとに名付けた28トークン

以上の色はすべて `starlight-input.yaml` の `palette:` に集約されている。生の rgba 値はここにしか書かれず、他は全てトークン参照である。現在28トークンで、命名は「`gray_<変換前の生の値>`」を基本にトレーサビリティを保ち、注記の濃淡ランプ専用値は `anno_*` として分けている:

```yaml
palette:
  gray_100: "rgba(113,114,116,1)"  # 62レイヤー横断の汎用色。単独の意味を持たない(0010 §4)
  gray_157: "rgba(164,166,168,1)"  # vt_motorway==1 / 高速自動車国道等(0018)
  gray_160: "rgba(167,169,171,1)"  # 国道(0018)
  gray_226: "rgba(227,229,231,1)"  # 都道府県道(0018)
  gray_233: "rgba(234,235,237,1)"  # 普通建物 塗り(0010 §2)
  gray_152: "rgba(160,161,163,1)"  # 高層建物 塗り(0010 §2)
  gray_209: "rgba(212,213,215,1)"  # 水域(WA)塗り。背景(zoom4-8)と偶然同値(0010 §4)
  anno_29:  "rgba(34,36,38,1)"     # 注記 最重要
  gray_30:  "rgba(35,37,39,1)"     # 軌道(RailTrCL)、普通鉄道/特殊鉄道/路面の鉄道
  gray_88_hydro: "rgba(92,93,95,1)" # 陸水面クラスタ専用。生の値はgray_88と同じだが独立
```

トークン設計にはひとつ規律がある。**値が偶然一致していても、意味が同じだと実データで裏付けられない限り別トークンにする**([0033](decisions/0033-new-token-policy.md))。`gray_88_hydro` はその典型で、水涯線・河川中心線などに現れる 88 は注記ランプの `gray_88` と数値上同じだが、「建物だけ少し明るくしたい」といった将来の編集が無関係な層を動かさないよう分離した。逆に `gray_161`/`gray_88` のように同じ `vt_code` が複数機構で同色に保たれていることを確認済みの組は、意図的な一致として共有する。`gray_100`/`gray_255` だけは62層横断の汎用色として自由に流用してよい、と明記している。

## 5. GSI の制作プロセスの推定 — 「共有テーブル+疎な例外」

`bvmap-dark` を分解して繰り返し現れたのが、**大きな共有テーブルを複数レイヤーへコピーし、個別レイヤーに後から小さな手作業の例外を足す**というイディオムである。独立した文脈で少なくとも次の4例が確認された:

1. **注記の `text-size`**: 全 `vt_code` を網羅する巨大な `match` を `シンボル付き100以上/100未満` の2層が丸ごと共有し、`100未満` だけに「ズーム14で 2941/2942 を1.3倍」が足されている([0008](decisions/0008-cartographic-layer-ordering.md))
2. **道路ティアの `line-color`**: ティア0〜4で `paint` はほぼ同一だが、ティア0の道路ケーシングだけ「`vt_rnkwidth` 不明は透明」の分岐を持つ(同、[0016](decisions/0016-tier-generator-stage1.md))
3. **鉄道の幅係数テーブル**: `鉄道中心線地下トンネル` の `line-width` に埋め込まれた `vt_rtcode` 別の係数(600/600/500/400/400/300/300)はティアの `鉄道中心線0` と数値まで一致し、トンネル側だけ「駅部分なら+800」が加わる([0025](decisions/0025-remaining-post-tier-13-layers-footprint.md))
4. **道路の幅員ランプ**: `道路中心線階段` の `line-width` の `vt_rnkwidth` ランプ(300/450/900/1800/2700)はティアの `道路中心線色0` と完全一致(同)

注記 `text-color` の `let` 包装(共有ランプ+ズーム14透明化)も同じ形であり、5例目と数えてよい。逆に、この癖の副作用と見られる痕跡もある。ティア4(`vt_lvorder >= 4` のオーバーフロー段)では、`vt_rtcode == "JR"` のような無関係な文字列比較まで `>=` に置換されている——「`==` を全て `>=` に置換する」粗い変換をティア4生成時にかけた副作用だろう([0016](decisions/0016-tier-generator-stage1.md))。ジェネレータはこの不整合を再現せず、`KNOWN_TIER4_ANOMALIES` として文書化した上で原文を保持している。

この帰納は実装方針を直接決めた。ジェネレータは「共有テーブル+レイヤーごとの疎な例外」を第一級の機能として持たねばならず、完全な純粋テンプレートを前提にすると破綻する([0009](decisions/0009-generator-architecture-direction.md))。同時に、「同じ名前・同じ役割に見える2つのレイヤーが実は別の構造を持つ」(ZL4-10 の国道層と高速層)ことも複数回起きたため、無理に1つの関数にパラメータで吸収せず、別の関数として並べる判断も繰り返した([0024](decisions/0024-zl410-dedicated-module.md))。

## 6. Starlight が変えたもの、変えなかったもの

### 変えなかったもの — 分類・階層・構造は継承すべき図式の知恵

第3〜5節で述べた分類論理(道路の三重構造、建物の3段階、注記の重要度ランプとズーム14例外、`vt_code` 種別+状態)、レイヤー順序、5ティアの立体交差表現、陸海の3層ダンス、ZL4-10 からの引き継ぎ、計曲線・主曲線の区別——これらは**一切設計し直していない**。ジェネレータの Stage 1 は「`bvmap-dark.json` の123レイヤーを順序も内容も byte-exact に再現できること」をゲートにし([0019](decisions/0019-stage1-final-assembly.md))、構造を理解し切ったことを証明してから配色に手を付けた。フォントも GSI 公式デジタル版の範囲(水域名のみ明朝)に留め、自然地形全般への拡張候補 `vt_code` は将来のために ADR に記録するだけにした([0013](decisions/0013-paper-map-revival-scope.md))。

### 変えたもの — 系統的なパレット変換

配色の変更は、個々の色を手で選ぶのではなく、全トークンに同一の変換式をかける形で行った([0030](decisions/0030-starlight-first-color-pass.md)):

```python
def cool_transform(r, g, b, cool=2.2):
    v = (r + g + b) / 3
    brighten = 0.03 if v < 100 else 0.09   # 暗い値(注記ランプ等)は控えめ、明るい値は強めに
    r2 = r + (255 - r) * brighten
    g2 = g + (255 - g) * brighten
    b2 = b + (255 - b) * brighten
    b2 += cool            # 青方向へわずかにシフト(銀灰色寄り)
    r2 -= cool * 0.6      # 赤方向を少し引く
    return (round(r2), round(g2), round(b2))
```

| トークン | `bvmap-dark` | `bvmap-starlight` |
|---|---|---|
| `gray_100`(汎用色) | 100,100,100 | 113,114,116 |
| `anno_29`(注記最重要) | 29,29,29 | 34,36,38 |
| `gray_233`(普通建物) | 233,233,233 | 234,235,237 |
| `gray_161`(等高線) | 161,161,161 | 168,169,172 |

設計上の要点は3つある。(1) `black`・`transparent`・`gray_255` は据え置き——黒は注記のコントラスト、白は背景の清潔さを守る。(2) 明度100未満の値(注記の重要度ランプ)は3%、100以上(道路・建物)は9%と**非対称に明るくする**——暗い文字色を大きく明るくすると可読性を損なうため。変換後もランプ 29〜98 の相対順序が保たれることを検証した。(3) 寒色シフトは R−1.3/B+2.2 程度の、色相変化としてはほぼ気づかない「質感」の変化に留めた。「明るめ・銀灰色寄り」を派手な着色ではなく階調の保存と微弱なティントで実現する、というのが Starlight の色の定義である。移行で新設するトークンにもこの変換を最初から適用し、変換済みと未変換の値が混在しないようにしている([0033](decisions/0033-new-token-policy.md))。

## 7. YAML から style.json へ(仕組みの概略)

`generator/` は Python の小さなモジュール群で、`python3 generator/assemble.py` を実行すると `style/bvmap-starlight.json` が書き出される。流れは次の通り:

- `load_input.py` が `starlight-input.yaml` を読み、`palette` でトークンを解決する
- `categories.*`(`engine: flat_match`)は `category_table.compile_match_expression()` で `["match", ["get", "vt_code"], ...]` に変換される。色・フォント名(`value_type: font_literal`)・数値(`value_type: number`)の3種の値に同じ機構を使う
- `priority_chains.*` は名前ごとに登録された専用ビルダー(`road_color.py`、`zl410_road_color.py`、`rail_tunnel_color.py`、`anno_symbol_color.py`)が判定順序・入れ子構造を持ち、YAML からは値だけを受け取る——「構造はコード、値は YAML」の境界([0020](decisions/0020-yaml-wiring-stage1.md))
- `layers:` の `engine: standalone` は `bvmap-dark.json` の該当レイヤーを base にし、指定 paint だけ生成結果へ差し替える。道路色・建物は `tier_template.py` が5ティア×14ロールへ機械展開する
- `patches:` は「なぜリテラルか」「未解明パターンが残るか」「色だけをパレット参照に差し替える」の3点だけを書く注釈付きの id 参照で、`step` 式の出力だけを差し替える `step_outputs` も持つ
- `assemble.py` が123層を元の順序で組み立て、id と順序の一致を唯一のハード条件として書き出す。生成 JSON 自体を必ずコミットし、ジェネレータが壊れても JSON を直接直せる逃げ道を残す([0009](decisions/0009-generator-architecture-direction.md))

## 8. 現状と未解決事項

2026-09-20時点で、123層中**108層が生成または YAML パッチ駆動、15層がリテラル**であり、`bvmap-starlight.json` は `bvmap-dark.json` と55層で内容が異なる(すべて意図した配色差分。構造は同一)。`LITERAL_RANGES`(配列位置による指定)は退役し、全123層が id で参照される([0035](decisions/0035-literal-ranges-retired.md))——上流の `hfu/stars` 側で `bvmap-dark.json` が並び替えられても壊れない。
